# Zenn 記事セルフレビュー

対象: $ARGUMENTS で指定された記事。未指定なら `git status` で変更中の `articles/*.md` を探す。

## 手順

1. 全文を通読し、記事が自分で立てている「定義・ルール・注意書き」をすべて書き出す
2. 下記チェックリストを順に実施する
3. 指摘を「誤り / 自己矛盾 / 曖昧 / コード不備 / 表記」に分類して報告し、修正を適用する
4. 最後に文体面を stop-ai-slop-jp スキルのチェックリストで通す

## チェックリスト

### 1. 自己矛盾(最優先)

- 記事前半で立てた定義・警告と、後半の例・判定・理由付けが同じ理屈で貫かれているか
- 特に「○×判定の理由」が、その概念の定義ではなく別の概念の定義にすり替わっていないか
  - 実例: 「冪等性 ≠ 決定論性」と警告しながら、冪等性×の理由を「実行するたびに結果が変わる」(決定論性の言い方)で書いていた
- 記事内の限定(「ここで言う〜とは」)と、本文の用語の使い方が食い違っていないか

### 2. 技術的な正確性

- 事実の主張は一次情報(RFC、公式ドキュメント、仕様書)と突き合わせる。二次記事の受け売りにしない
- 廃止された仕様(例: RFC 7231 → RFC 9110)を現行版と取り違えていないか。旧番号は言及に留め、リンクは現行版に張る
- 一般的な用語法とずれる定義を使う場合は「ここで言う〜とは」とスコープを明示しているか

### 3. 定義の一貫性

- 同じ概念の定義が複数箇所(節冒頭・比較表・まとめ)に出る場合、文言を揃える。節冒頭の定義を正とする
- まとめの箇条書きは「定義 → ご利益」の順。ご利益の説明を定義の位置に置かない

### 4. コード例

- 算術・出力コメントを頭の中で実行して検証する。怪しければ実際に実行する
- 未定義の型・変数・関数がないか。スニペット間で同名の別物(コンポーネント名と型名など)が衝突していないか
- 関数名・変数名が記事全体で統一されているか(前半と後半で別名になっていないか)
- コードフェンスの言語指定が内容と一致しているか(HTTP 疑似コードに typescript を付けない)

### 5. 読者の反論の先回り

- 詳しい読者がコメント欄で突っ込みそうな点は、本文か `:::message` ボックスで先に回収する
  - 実例: DELETE 2 回目の 404、POST の Idempotency-Key、intended effect のスコープ

### 6. 表記・体裁

- 数字の全角/半角、「n つ」の表記を記事内で統一する
- frontmatter: topics は発見性を考慮(typescript, react などフォロワーの多いタグ)。published の状態も確認
- 句読点スタイル(，．)や絵文字の使い方は書き手の声なので、勝手に変えない

## 報告フォーマット

- 冒頭に指摘の総数と、重要度順の要約
- 各指摘: 何が・なぜ問題か・どう直したか
- 「疑ったが問題なし」と判断した箇所も明記する(レビューの網羅性を示すため)
